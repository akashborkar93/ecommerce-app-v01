# E-Commerce API

A small e-commerce backend (products, customers, orders) built with FastAPI, SQLAlchemy and PostgreSQL. It is packaged as a Docker image and configured entirely through environment variables, so the same image runs against a local PostgreSQL or Amazon RDS PostgreSQL with no code changes.

This repository contains the **application only**. AWS infrastructure is not created by this repo. For deploying to AWS (EC2 + Docker + RDS + ALB), follow [docs/AWS_DEPLOYMENT_GUIDE.md](docs/AWS_DEPLOYMENT_GUIDE.md): the image is built and run on the EC2 instance itself, so no local commands are needed. See also the [Deployment contract](#deployment-contract).

## Architecture

```
Client
  |
  v
FastAPI  (/products, /orders, /customers, /health, /ready)
  |
  v
PostgreSQL
```

```
app/
  api/       HTTP routers (thin)
  services/  business logic (order totals, stock handling)
  models/    SQLAlchemy models
  schemas/   Pydantic request/response models
  db/        engine, session, declarative base
  core/      config, logging, errors, request middleware
  main.py    app factory
migrations/  Alembic migrations
scripts/     seed.py (manual demo data)
tests/       pytest suite
```

## API

Interactive docs: `GET /docs` (Swagger UI) and `GET /openapi.json`.

| Method | Path | Description | Errors |
|---|---|---|---|
| GET | `/products` | List products (`category`, `limit`, `offset`) | |
| GET | `/products/{id}` | Get a product | 404 |
| POST | `/products` | Create a product | 422 |
| POST | `/customers` | Create a customer | 409 duplicate email, 422 |
| GET | `/customers` | List customers (`limit`, `offset`) | |
| GET | `/customers/{id}` | Get a customer | 404 |
| POST | `/orders` | Create an order | 400 unknown customer/product, 409 insufficient stock, 422 |
| GET | `/orders` | List orders (`customer_id`, `limit`, `offset`) | |
| GET | `/orders/{id}` | Get an order with its items | 404 |
| GET | `/health` | Liveness: process is up (no DB check) | |
| GET | `/ready` | Readiness: database reachable | 503 |

Creating an order: the server computes `total_amount` from current product prices; any client-supplied total is ignored. Each item's price is snapshotted into the order. Stock is decremented atomically and the whole order succeeds or fails together. Repeated product lines are merged.

```json
POST /orders
{ "customer_id": 1, "items": [ { "product_id": 3, "quantity": 2 } ] }
```

All errors share one shape:

```json
{ "error": { "code": "insufficient_stock", "message": "...", "request_id": "..." } }
```

Unexpected errors return a generic 500 message; details go to the logs only. Authentication is intentionally not implemented yet.

## Configuration

All configuration comes from environment variables (a local `.env` file is also read for development; see `.env.example`).

| Variable | Required | Default | Description |
|---|---|---|---|
| `DATABASE_HOST` | yes | | PostgreSQL host |
| `DATABASE_PORT` | no | `5432` | PostgreSQL port |
| `DATABASE_NAME` | yes | | Database name |
| `DATABASE_USER` | yes | | Database user |
| `DATABASE_PASSWORD` | yes | | Database password |
| `APP_ENV` | no | `development` | Environment label |
| `LOG_LEVEL` | no | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR` |
| `PORT` | no | `8000` | Port the container listens on |
| `DATABASE_CONNECT_TIMEOUT` | no | `5` | Seconds to wait when connecting to the DB |

The app refuses to start if a required variable is missing.

## Database

Tables: `customers`, `products`, `orders`, `order_items`.

```
customers 1 --- * orders 1 --- * order_items * --- 1 products
```

| Table | Columns |
|---|---|
| customers | id, name, email (unique), created_at |
| products | id, name, description, price, stock, category, created_at, updated_at |
| orders | id, customer_id, total_amount, status, created_at |
| order_items | id, order_id, product_id, quantity, price |

Money uses `NUMERIC`/`Decimal`, never floats. Check constraints enforce `price > 0`, `stock >= 0`, `quantity > 0`.

### Migrations (Alembic)

The app never creates or alters tables on startup. Run migrations explicitly:

```bash
alembic upgrade head          # apply all migrations
alembic current               # show the applied revision
alembic revision --autogenerate -m "describe change"   # create a new migration, then review it
alembic downgrade -1          # roll back one migration
```

Rollback notes:
- Always review autogenerated migrations before applying them.
- `downgrade` of the initial migration drops all tables and their data. Treat downgrades as destructive and take a backup first.
- Prefer additive, backwards-compatible migrations (add a column, then backfill, then switch code) so a bad release can be rolled back without a schema downgrade.

### Seed data

Load demo products (Wireless Headphones, Smart Watch, Laptop, Water Bottle) manually. It is safe to re-run; existing products are skipped:

```bash
python -m scripts.seed
```

It is never run on application startup.

## Running locally

Requires Python 3.11+ and a reachable PostgreSQL.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
cp .env.example .env               # then fill in the DATABASE_* values
alembic upgrade head
python -m scripts.seed             # optional
uvicorn app.main:app --reload --port 8000
```

### Interactive frontend

The React/Vite dashboard runs separately during local development:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The Vite development server proxies `/products`, `/customers`, `/orders`, `/health`, and `/ready` to FastAPI at `http://127.0.0.1:8000`, so FastAPI must be running first.

## Testing

```bash
pytest -q
```

By default tests use an in-memory SQLite database, so no PostgreSQL is needed. To run the same suite against a real PostgreSQL (use a throwaway database; tables are dropped):

```bash
TEST_DATABASE_URL="postgresql+psycopg://user:pass@host:5432/test_db" pytest -q
```

Covered: health, readiness (including DB failure), products (list/get/create/not found/validation), orders (create/get/list/invalid product/invalid customer/insufficient stock/atomic rollback), error handling and logging.

## Current limitations and upcoming roadmap

The current repository is intentionally limited to the core products, customers, and orders workflow. The following features are planned for upcoming development sessions:

- Authentication and authorization: API authentication, protected endpoints, role-based access, and permission enforcement.
- User accounts: associate customers with users and support account registration, login, password reset, and profile management.
- Product management: update and delete products, and manage categories and product availability.
- Order lifecycle: order status transitions, cancellation, refunds, shipping, and order history for authenticated users.
- Shopping cart: cart persistence, add/remove items, quantity updates, and checkout.
- Inventory improvements: reservations, stock history, and inventory replenishment workflows.
- Payment processing: payment provider integration and secure payment status handling.
- Pagination metadata: structured page totals and navigation links instead of only `limit` and `offset`.
- Data lifecycle: soft deletion, audit trails, and retention policies.
- Background processing: asynchronous jobs for notifications, emails, payments, and long-running operations.
- Caching: cache frequently read catalog data and configure cache invalidation.
- Observability: distributed tracing, metrics dashboards, alerts, and centralized log collection.
- CI/CD: automated testing, linting, image builds, security scans, and deployment pipelines.
- Deployment improvements: ECS/Fargate or Kubernetes deployment and native secret injection.
- Schema evolution: additional Alembic migrations for new models and backward-compatible database changes.

These items are not implemented unless explicitly changed in a later session. Authentication is not currently implemented, and API endpoints are therefore open.

## Docker

These commands run wherever Docker is available, from the folder that contains the `Dockerfile` (the project root). For AWS, that is the cloned repo folder on the EC2 instance, as described in the [AWS deployment guide](docs/AWS_DEPLOYMENT_GUIDE.md); you do not need to run them on your own PC.

```bash
docker build -t ecommerce-api:latest .

# apply migrations (one-off)
docker run --rm \
  -e DATABASE_HOST=... -e DATABASE_NAME=... -e DATABASE_USER=... -e DATABASE_PASSWORD=... \
  ecommerce-api:latest alembic upgrade head

# run the API
docker run --rm -p 8000:8000 \
  -e DATABASE_HOST=... -e DATABASE_NAME=... -e DATABASE_USER=... -e DATABASE_PASSWORD=... \
  -e APP_ENV=production -e LOG_LEVEL=INFO \
  ecommerce-api:latest
```

Design decisions:
- **Multi-stage, `python:3.11-slim`**: dependencies are built into wheels in a builder stage; the runtime image contains no build tooling and stays small.
- **Non-root**: runs as user `app` (UID 10001) with no login shell.
- **No secrets in the image**: nothing is baked in; `.dockerignore` excludes `.env` files, tests, and git data. All config is injected at runtime.
- **Configurable port** via `PORT` (default 8000). `exec` makes uvicorn PID 1 so it receives `SIGTERM` and shuts down cleanly.
- **Migrations are a separate command**, not part of container startup, so starting the app can never alter the schema.
- The image has no `HEALTHCHECK`; health is checked externally via `/health` and `/ready`.

## Deployment contract

This is the interface between the application and whoever deploys it.

| Item | Value |
|---|---|
| Container port | `8000` (override with `PORT`) |
| Start command | `uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000}` (the image default `CMD`) |
| Liveness | `GET /health` returns 200 `{"status":"healthy"}` |
| Readiness | `GET /ready` returns 200 `{"status":"ready"}`, or 503 `{"status":"not_ready"}` if the DB is unreachable |
| Environment variables | `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_USER`, `DATABASE_PASSWORD`, `APP_ENV`, `LOG_LEVEL` (plus optional `PORT`, `DATABASE_CONNECT_TIMEOUT`) |
| Database | External PostgreSQL 13+, reachable from the container, with the target database and user already created |
| Migrations | Run `alembic upgrade head` once per release, before or alongside starting the new version |
| Logs | JSON lines on stdout: `timestamp`, `level`, `service`, `request_id`, `method`, `path`, `status_code`, `duration_ms`, error info |
| Request tracing | Honors an incoming `X-Request-ID` header and echoes it in the response |

Notes for the deployer:
- Point load balancer health checks at `/ready` (or `/health` if you do not want DB outages to pull instances out of rotation).
- `/ready` fails within `DATABASE_CONNECT_TIMEOUT` seconds (default 5) when the database is unreachable; keep your health-check timeout above that.
- The app does not terminate TLS; do that at the load balancer.
- Pass `DATABASE_PASSWORD` via your platform's secret mechanism rather than plain configuration.
